# Rotation Humanization Engine Plan

## Implementation status

The first compatibility slice is now in progress:

- added rich, owner-aware rotation request/target/purpose/validity models;
- added an opt-in deterministic trajectory core with cubic geometry, minimum-jerk timing, bounded retargeting, and correlated drift;
- added `Off`, `Subtle`, `Balanced`, and `Custom` settings while keeping `Off` as the compatibility default;
- routed the new engine through the central server/client rotation limiter;
- migrated KillAura and ProjectileAimbot to attach stable entity target metadata;
- replaced Zig-Zag/LazyFlick candidate perturbation with a seeded sticky normalized target point;
- removed `RandomizationSettings` and its combat-module configuration surface;
- added a dependency-free pure-math verification harness;
- compilation is awaiting the maintainer-run build checkpoint; no Gradle command should be run by the implementing agent.

Legacy prediction remains temporarily in place until the target-persistence slice compiles and its behavior is confirmed.

## Goal

Replace the current collection of stateless rotation randomizers with one stateful, deterministic, testable engine that produces smooth and imperfect rotation trajectories while preserving LiquidBounce's functional requirements:

- the requested target remains reachable and raycast-valid when a module needs it to be;
- yaw wraps correctly, pitch stays in range, and mouse-sensitivity quantization is applied exactly once;
- server-side and client-side rotations continue to use the same request lifecycle;
- moving targets can be followed without rebuilding a visibly unrelated path every tick;
- reset-to-player motion is generated by the same engine instead of a separate special case;
- modules can opt out for actions that must be immediate or exact.

This is a rotation-quality project, not a promise that generated input is indistinguishable from a person. The implementation should optimize for coherent motion, predictable gameplay, and measurable kinematics. It should not add statistical performance moderation, headshot-rate manipulation, honeytoken handling, or an arms race against particular anti-cheats.

## Constraints discovered in this client

Minecraft 1.8.9 normally exposes one meaningful rotation update per game tick (20 Hz), not the hundreds or thousands of samples available to desktop cursor libraries or USB firmware. A direct port of pixel-space mouse algorithms would therefore alias into a few large samples and lose most of its intended behavior. The engine must operate in unwrapped yaw/pitch angle space and treat ticks as its sampling interval.

The current flow is:

1. A module finds a point/rotation, commonly through `RotationUtils.searchCenter`.
2. The module calls `RotationUtils.setTargetRotation(rotation, settings)`.
3. The global `RotationUtils` singleton owns one `targetRotation`, one `currentRotation`, and one `activeSettings` request.
4. On `RotationUpdateEvent`, `update()` calls `limitAngleChange`/`performAngleChange`, then sensitivity-quantizes the result.
5. `MixinEntityPlayerSP` uses `currentRotation` when choosing C05/C06 packet yaw and pitch, and updates `serverRotation` after sending.
6. `RotationUtils.onPacket` replaces a rotating C03 packet's rotation and records short-stop state.
7. When the request expires, the same limiter moves back toward the player's camera until the reset threshold is satisfied.

This central request point is a good integration seam. It is also currently too lossy: a bare `Rotation` contains no target identity, hitbox, selected hit point, action deadline, or validity policy, so a later engine cannot distinguish a moving entity from an exact block placement.

## Evaluation of the referenced repositories

The repositories were inspected at source level, not just from their READMEs.

| Reference | What it actually does | Ideas worth carrying over | What not to port literally |
|---|---|---|---|
| [JoonasVali/NaturalMouseMotion](https://github.com/JoonasVali/NaturalMouseMotion) | Breaks a move into one or more movement legs, selects a normalized speed `Flow`, adds a sinusoidal path deviation and accumulated random noise, fades effects near an endpoint, and optionally creates overshoot/correction legs with a reaction pause. | Separate planning from sampling; explicit movement legs; endpoint fade; interchangeable motion profiles; exact final correction. | Default time is only weakly distance-aware, fixed overshoot count is conspicuous, flow tables are ad hoc, and independent accumulated x/y noise is not suitable for yaw/pitch. |
| [barrybingo/CNaturalMouseMotion](https://github.com/barrybingo/CNaturalMouseMotion) | A close C++ port with named natures such as fast gamer, average user, granny, and robot. | A profile should be a coherent parameter bundle rather than unrelated toggles. | It inherits the Java model's limitations and contains port-specific hazards (for example, the inspected move loop adds `noise.y` to both noise accumulators). Do not copy code or constants. |
| [Xetera/ghost-cursor](https://github.com/Xetera/ghost-cursor) | Builds a cubic Bézier whose two randomized anchors are kept on one side of the direct line; samples a random point inside the target box; uses a Fitts-like distance/target-width term for sample count; and performs a separate overshoot/correction curve above a fixed distance threshold. | One-sided control points; target-area-aware timing; sticky point selection within a valid region; correction as a separate phase; revalidate a target that moved. | Its `steps` formula is not a physical Fitts-law movement time, the 500 px overshoot step is discontinuous, and uniformly sampled Bézier LUT points do not by themselves create a human velocity profile. |
| [bn-l/ghost-cursor-play](https://github.com/bn-l/ghost-cursor-play) | A Playwright fork of the same core path logic with fewer of the newer upstream timing features. | Confirms that browser integration should be an adapter around a path core. | It adds little algorithmically and retains fixed thresholds/global randomness. Treat it as an integration example, not an independent model. |
| [CloverLabsAI/human-cursor](https://github.com/CloverLabsAI/human-cursor) | Generates a high-degree Bézier through 2–10 random knots in an expanded rectangle, distorts intermediate y values with Gaussian samples, then resamples through a randomly chosen easing function. | An explicit pipeline (knots/path, distortion, temporal resampling); weighted profile parameter selection; preserving exact endpoints. | Random knots can produce excessive curvature, distortion is only on the y axis and has a positive default mean, many unrelated easing functions create inconsistent profiles, and fixed 35–79/100 point counts are meaningless at 20 Hz. |
| [DefinitelyN0tMe/Macronyx](https://github.com/DefinitelyN0tMe/Macronyx) | Has two separate features: uniform timing/position variance (`Humanizer`) and cubic Bézier playback (`MouseCurveGenerator`). The curve uses same-side perpendicular offsets, 5–20 distance-adaptive points, selectable easing, and a deterministic distance threshold for overshoot. | Small cubic curve; tangent/perpendicular coordinates; distance-adaptive duration; clean separation between playback and curve generation. | Its generic `humanize` is iid uniform noise; position offsets move the endpoint itself; overshoot is enabled for every eligible move rather than being contextual; “natural” easing is only ease-out. |
| [VoltCyclone/Hurra](https://github.com/VoltCyclone/Hurra) | Queues fixed-point movement substeps, conserves the final remainder, applies delivery error/onset delay, uses an adaptive IIR velocity-debt filter, soft saturation, an overshoot correction entry, and runtime layered sine/LFSR tremor. Modes reseed some parameters from hardware randomness. | Conservation of commanded movement; persistent state; smooth saturation; bounded queue/fallback behavior; separating motion debt from output perturbation; extensive stress/invariant testing. | It runs at roughly 1 kHz, so its frame counts and tremor bands cannot map to 20 Hz. Fixed mode ranges, fixed 10% overshoot, xorshift/LFSR noise, and stable oscillator frequencies create avoidable signatures. Its documentation also disagrees with current code in places (documented four levels versus current off/micro/full modes and different parameter values), so source must remain authoritative. |

The common lesson is that state, phases, endpoint constraints, and context matter more than adding randomness. None of the repositories is a drop-in model for tick-based Minecraft rotations.

## Current option audit and migration decisions

### `Legitimize`: remove

Verdict: the intent is reasonable, but the implementation is not a coherent model and the option name hides several unrelated behaviors.

Current behavior and problems:

- The purported 0.9–1.1 “imperfect correlation” multiplications in `performAngleChange` discard their results, so this section is a no-op.
- Per-tick yaw and pitch jitter is outside the `legitimize` branch and therefore affects every nonzero limited rotation, even when `Legitimize` is false.
- Slowdown interpolates from the previous delta using a newly sampled uniform factor every tick. It has no persistent velocity, acceleration, phase, or movement identity.
- The base limiter travels at an approximately constant angular magnitude until one axis clamps, rather than following an acceleration/deceleration profile.
- `isDifferenceAcceptableForReset` changes reset semantics based on `legitimize`, coupling a cosmetic toggle to request lifetime.
- Aimbot has its own copy of the option and bypasses `RotationSettings`, so behavior differs by caller.

Migration: delete `legitimizeValue`, the `legitimize` parameter, and the old `applySlowDown` realism branch after the new engine covers both normal travel and reset travel. Do not silently map the boolean to a high-strength preset; migrate `false` to `Humanization=Off` and `true` to `Humanization=Balanced`, with a one-release config alias only if the configuration framework supports aliases safely.

### `RandomizationSettings`, `Zig-Zag`, and `LazyFlick`: remove

Verdict: remove the class after migration.

Problems:

- It perturbs the reference rotation used to rank hitbox scan candidates, rather than planning a continuous path to a stable target point. The result can jump between unrelated scan cells.
- Chance uses `Math.random() > chance`; with the default 0.8–1.0 range, activation is 0–20%, contrary to the intuitive reading of “chance.”
- Zig-Zag can request 5–10 degree discontinuities, then only sensitivity-quantizes them.
- LazyFlick's pitch expression adds a positive 5–10 degree value to a sign, introducing a strong directional bias.
- It samples only three historical rotations, chooses one history entry randomly for the intercept check, has no engagement state, and uses several unrelated global random sources.
- Its values are exposed only by KillAura and ProjectileAimbot, while the actual limiter adds different random behavior to every `RotationSettings` consumer.

Migration: delete `RandomizationSettings.kt`, remove its arguments from `searchCenter`, and replace it with a persistent target-point policy in `RotationRequest`. Configs using a non-`None` pattern migrate to `Humanization=Balanced`; advanced numeric fields are intentionally discarded.

### `SimulateShortStop`: remove as a standalone feature

Verdict: pauses can be useful as a planned correction or settling phase, but the current accumulated-yaw threshold and attempt counter are deterministic and globally coupled through `WaitTickUtils`.

Migration: remove `simulateShortStopValue`, threshold/attempt/duration fields, and packet-side yaw accumulation. If pauses are retained, the engine planner may produce a bounded `SETTLE` phase based on movement state and deadline, never a fixed threshold exposed as a separate anti-pattern toggle.

### Aimbot `Jitter`: remove

Verdict: iid per-tick Gaussian camera changes, sampled independently per axis with a shifted mean (`nextGaussian() - 0.5`), are not useful humanization. The new engine owns all motion perturbation.

### `OutBorder`: keep only as an explicit non-humanized targeting behavior

`OutBorder` intentionally chooses coordinates outside the normal hitbox interpolation range. That is not humanization. Keep it only if it has a distinct functional use, rename/document it as a targeting mode, and force humanization off for that request if exact behavior is required. Do not fold it into a humanization profile.

### `GenerateSpotBasedOnDistance`: replace

Its nearest-hitbox-point behavior is useful for reach and visibility, but it should become the deterministic feasibility seed for a sticky target-point sampler, not an independent “human” toggle.

### Prediction: keep the capability, replace the implementations

Prediction improves correctness for moving targets and projectiles; it is not randomization and should not be removed wholesale. The current implementations should be removed because they are duplicated and inconsistent:

- `toRotation(vec, predict)` calls immutable `Vec3.addVector(...)` without assigning the result, so this prediction flag currently has no effect.
- KillAura, Aimbot, and TimerRange offset the target box with one-tick displacement multiplied by `2 + PredictEnemyPosition`; setting the option to zero still predicts two ticks, and a negative setting is allowed.
- Client prediction mutates the real player's current/previous positions temporarily around `searchCenter`, which is fragile and obscures coordinate ownership.
- `faceTrajectory` projects the target by `predictSize`, the player by only one tick, and uses a single velocity sample. It does not solve target time-of-flight iteratively or handle acceleration/teleports robustly.
- `searchCenter(..., predict)` means “offset the observer,” while module fields named prediction mean target extrapolation, producing ambiguous APIs.

Replacement:

- Introduce `TargetMotionEstimator`, independent of the humanization engine.
- Track a short, timestamped position history per entity and estimate relative velocity with a robust exponentially weighted filter. Reset on teleport, world change, spawn/death, or implausible displacement.
- For melee/view targeting, predict relative position for an explicit horizon derived from request latency (normally 0–2 ticks), clamped by confidence and target age.
- For projectiles, solve flight time and target position together for a bounded number of iterations; account for shooter and target relative motion consistently. Fall back to the unpredicted ballistic solution when no valid solution exists.
- Expose `PredictionMode = Off | Latency | Projectile` and a small `PredictionHorizonTicks` range only where appropriate. No generic Boolean `predict` argument remains in `toRotation` or `searchCenter`.
- Feed the estimated target point into humanization. Never randomize the prediction itself; uncertainty should reduce the prediction horizon and widen the safe target region, not add noise.

## Proposed architecture

### 1. Rich rotation requests

Replace the bare target setter internally with a request model. Preserve a compatibility overload during migration.

```kotlin
data class RotationRequest(
    val owner: Any,
    val desired: Rotation,
    val settings: RotationSettings,
    val target: RotationTarget? = null,
    val purpose: RotationPurpose = RotationPurpose.GENERIC,
    val deadlineTick: Int? = null,
    val validity: RotationValidity = RotationValidity.NONE,
    val priority: Int = 0
)

sealed interface RotationTarget {
    data class EntityRegion(
        val entityId: Int,
        val box: AxisAlignedBB,
        val allowedBodyRange: ClosedFloatingPointRange<Double>,
        val allowedHorizontalRange: ClosedFloatingPointRange<Double>
    ) : RotationTarget
    data class WorldPoint(val point: Vec3) : RotationTarget
    data class ExactRotation(val rotation: Rotation) : RotationTarget
}
```

Use stable owner identity and priority instead of mutable `prioritizeRequest`, `immediate`, and `instant` flags stored on shared settings objects. A request refresh from the same owner updates the target without starting a new movement. A different owner, target entity, purpose, or world epoch starts a new movement or an explicit handoff.

`RotationPurpose` should at least distinguish `COMBAT_TRACK`, `PROJECTILE`, `BLOCK_INTERACT`, `PLACE`, `RESET`, and `GENERIC`. Purpose selects constraints, not a hidden per-module algorithm.

### 2. Pure engine with explicit state

Create a Minecraft-independent core:

```kotlin
interface RotationHumanizer {
    fun begin(input: BeginInput): HumanizationState
    fun retarget(state: HumanizationState, input: RetargetInput)
    fun step(state: HumanizationState, input: StepInput): RotationStep
    fun reset(state: HumanizationState)
}
```

`HumanizationState` owns:

- session/profile parameters and a seeded `Random` instance;
- movement id, phase (`REACTION`, `PRIMARY`, `OVERSHOOT`, `CORRECTION`, `SETTLE`, `COMPLETE`), and phase progress;
- unwrapped start/current/goal yaw and pitch;
- velocity and acceleration in angle space;
- planned duration and curve control points;
- sticky target-point coordinates normalized inside a target box;
- colored-noise state and quantization remainder;
- last request owner/target/purpose/world epoch;
- validity/fallback counters and debug samples.

The pure core must not read `mc`, global `RotationUtils`, system time, `Math.random()`, or `WaitTickUtils`. The adapter supplies tick delta, target updates, sensitivity step, and raycast feedback. A fixed seed must reproduce the same trajectory.

### 3. Coordinate system and path shape

- Unwrap target yaw to the nearest representation relative to current yaw before planning. Never interpolate wrapped degrees directly across ±180°.
- Treat `(yaw, pitch)` as a 2D local plane for short rotations. Clamp pitch validity after every candidate step.
- Build a cubic path with control points at roughly the first and second thirds of the displacement. Offset both primarily along one shared normal side, with bounded tangent variation. This takes the robust idea from ghost-cursor/Macronyx without permitting arbitrary high-degree loops.
- Scale curvature continuously with angular distance, target angular width, purpose, and profile. Curvature must fade toward zero for tiny moves and exact placement actions.
- Parameterize geometry and time separately. Path position uses either minimum-jerk progress `s(u) = 10u^3 - 15u^4 + 6u^5` or a similarly monotone profile. Do not assume uniformly sampled Bézier `t` means a plausible speed.
- For a moving goal, preserve current position and velocity. Small target changes update the terminal point/control points continuously; large jumps or invalid targets replan with a C1-continuous handoff. Do not restart reaction delay on every refresh.

At 20 Hz, a full curve needs enough duration to exist. Moves planned for fewer than three samples should use a bounded acceleration/velocity stepper rather than manufacturing a one-tick arc.

### 4. Movement duration and speed limits

Keep user-configured horizontal/vertical maximum angle changes as hard capability limits, but sample them once per movement/profile rather than every tick.

Calculate a desired duration from:

- angular distance `D`;
- angular target width `W` (derived from safe hitbox samples when available);
- a Fitts-inspired term `a + b * log2(D / max(W, epsilon) + 1)`;
- current angular velocity, purpose, deadline, and profile variation.

Clamp duration so the generated path cannot exceed horizontal/vertical limits. A request with a hard action deadline may shorten the plan within limits, reduce nonessential curvature/noise, or fall back to the deterministic limiter. It must never silently miss the deadline for cosmetic realism.

### 5. Target-point persistence and validity

Refactor `searchCenter` into two responsibilities:

1. `RotationTargetResolver` computes the visible/reachable region and deterministic nearest feasible fallback.
2. `TargetPointTracker` selects and retains a normalized point inside that region for the engagement.

Rules:

- Sample from an inset safe region, biased toward the current crosshair/nearest reachable point rather than uniformly across the full box.
- Keep the same normalized point while the entity box moves. Add only slow bounded drift within the safe region.
- Change the point when it becomes occluded/unreachable, the configured body region changes, a correction phase completes, or a bounded dwell period expires.
- Before emitting a combat/action rotation, sensitivity-quantize it and raycast the quantized result. If invalid, project toward the nearest valid sample or use the deterministic fallback.
- Overshoot points may temporarily leave the valid region only when the request has time to correct before the action deadline. Placement and exact-interaction purposes default to no overshoot.

This replaces candidate hopping from `RandomizationSettings` and prevents endpoint noise from turning a valid rotation into a miss.

### 6. Imperfection model

Use a small number of stateful effects, all profile-scaled and envelope-shaped:

- **Path bias:** the cubic normal offset is the primary large-scale imperfection.
- **Low-frequency drift:** a bounded first-order correlated process in tangent/normal coordinates, sampled once per tick. Its amplitude fades near exact endpoints and is lower for pitch than yaw unless learned data supports otherwise.
- **Micro-correction:** zero or one short correction phase when terminal error, target motion, or a planned overshoot warrants it. Corrections are goal-directed, not random sign flips.
- **Overshoot:** optional and continuously conditioned on distance, approach speed, target width, purpose, and available deadline. Magnitude is bounded by the target's angular scale. No fixed distance step or fixed per-mode probability.
- **Reaction delay:** only on a genuinely new voluntary request, represented in whole ticks and normally overlapping with target observation. At 20 Hz, broad millisecond distributions are false precision; default combat profiles should use a small probability of a one-tick onset, while exact/urgent actions use zero.

Do not implement 4–12 Hz tremor, pink-noise spectra, Voss-McCartney, logistic chaos, Poisson micro-corrections, or the twelve-stage pipeline from `HUMANIZATION.md` in the first implementation. At 20 Hz these are hard to identify separately, easy to alias, and unsupported by client-specific measurements. Add an effect only after recorded-data analysis shows a gap that the simpler model cannot cover.

Never add iid output jitter after planning. Any perturbation is part of state and must respect the final validity envelope.

### 7. Sensitivity quantization and conservation

- Perform all planning in high precision (`Double` internally).
- Apply Minecraft sensitivity quantization exactly once at the adapter boundary, relative to the last server rotation for server-side requests or last camera rotation for client-side requests.
- Carry fractional quantization error in state (error diffusion) so sub-GCD motion is delayed rather than independently rounded away every tick.
- Quantize before raycast validation.
- Guarantee finite values, pitch in `[-90, 90]`, nearest-yaw travel, and no step beyond configured axis limits plus one GCD tolerance.
- On completion, settle at the nearest sensitivity-representable valid rotation; do not force an unreachable mathematical endpoint.

### 8. Session parameters and profiles

Expose a small UI instead of dozens of statistical knobs:

- `Humanization`: `Off`, `Subtle`, `Balanced`, `Custom` (default `Off` for backward compatibility during rollout; reconsider after validation).
- `Response`: a bounded speed/duration scale.
- `PathVariation`: maximum normal curvature scale.
- `CorrectionTendency`: low/medium/high mapped to bounded planner parameters.
- `TargetDrift`: bounded sticky-point drift, not output jitter.

Keep hard functional controls such as rotations enabled, server-side application, strafe correction, keep/reset behavior, and horizontal/vertical speed limits outside the humanization group.

A profile samples a correlated parameter bundle once per world/session and small movement-level deviations once per new movement. Do not independently randomize every bound every tick. Seed from a session seed, expose the active seed in debug mode, and allow a fixed developer seed for reproduction.

## Implementation phases

### Phase 0 — Measurement harness and safety net

1. Add `RotationTelemetry` behind a developer/debug flag. Record tick, request/movement id, raw goal, planned output, quantized output, server output, phase, target validity, angular velocity/acceleration/jerk, path length, and seed.
2. Extend RotationRecorder or add a CSV/JSON exporter for both real manual rotations and generated trajectories. Keep this local and opt-in.
3. Add a headless pure-math test source set (or the minimal Kotlin test dependency) so trajectory logic can run without launching Minecraft.
4. Capture representative scenarios: 2°, 15°, 90°, and wraparound moves; stationary/moving targets; target switch; reset; 30/60/180° speed caps; several sensitivities; exact block placement.

Exit criterion: current behavior is reproducibly captured, and the test harness can assert angle/GCD/validity invariants.

### Phase 1 — Request model and deterministic baseline

1. Introduce `RotationRequest`, ownership/priority, purpose, deadline, and validity.
2. Move arbitration out of mutable `RotationSettings` flags.
3. Implement `Humanization=Off` through the new engine as a deterministic acceleration/velocity-limited baseline matching current functional behavior.
4. Unify server-side, camera-side Aimbot, and reset travel through the coordinator.
5. Fix immutable eye-position prediction misuse even before advanced prediction lands.

Exit criterion: all existing consumers work with humanization off; packet, strafe, reset, and exact-action behavior are regression-tested.

### Phase 2 — Core trajectory engine

1. Add unwrapped angle geometry, minimum-jerk temporal progress, cubic path planning, and persistent velocity.
2. Add movement duration from angular distance/width with hard speed/deadline constraints.
3. Add deterministic seed handling and Subtle/Balanced profiles.
4. Implement continuous retargeting and target-switch handoff.
5. Add correlated drift with endpoint envelope, then optional overshoot/correction phases.
6. Add quantization error diffusion and quantized-output validation.

Exit criterion: trajectories pass property tests, remain continuous under retargeting, and show bell-shaped speed without exceeding caps.

### Phase 3 — Target region and prediction

1. Split hitbox feasibility from target-point choice.
2. Add sticky normalized target points, safe insets, bounded drift, and revalidation.
3. Add entity motion history and confidence-aware latency prediction.
4. Add iterative projectile interception and fallback.
5. Integrate KillAura, Aimbot, and ProjectileAimbot; validate attack/action deadlines against quantized raycasts.

Exit criterion: a moving target does not cause cell hopping or path restarts, and prediction degrades cleanly on teleports/noisy history.

### Phase 4 — Migration and removal

1. Migrate remaining rotation consumers by purpose.
2. Add config aliases/migration notes where feasible.
3. Remove `Legitimize`, `RandomizationSettings`, Zig-Zag, LazyFlick, Aimbot Jitter, short-stop settings, and old prediction plumbing.
4. Remove compatibility overloads once all call sites use rich requests.
5. Update English localization/descriptions and any config documentation.

Exit criterion: `rg` finds no legacy option or old Boolean prediction call, and old configs load without crashing or producing invalid values.

### Phase 5 — Calibration and rollout

1. Compare generated versus opt-in manual traces using the same scenario buckets.
2. Tune only broad profile bundles; avoid target-server or anti-cheat presets.
3. Run multiplayer/manual regression checks for packet cadence, movement correction, raycasts, scaffold placement, inventory pauses, world changes, death, and module disable.
4. Roll out with `Off` as the safe default and a debug overlay/telemetry switch. Promote a default profile only after gameplay and statistical validation.

## Verification strategy

### Deterministic unit and property tests

- Same seed and inputs produce byte-for-byte identical samples; different seeds stay within the same constraints.
- Yaw uses the shortest wrapped path for cases around ±180°.
- Pitch never leaves `[-90°, 90°]`; no NaN or infinity is emitted.
- Output per axis never exceeds configured limits plus one sensitivity step.
- Quantized deltas are integer multiples of the sensitivity GCD relative to the correct prior rotation.
- Error diffusion has no long-term directional bias and settles rather than oscillating.
- Minimum-jerk progress is monotone and starts/ends with low velocity.
- A cubic path has no loops or direction reversal unless it is explicitly in an overshoot/correction phase.
- Retargeting preserves position and bounded velocity; refreshing the same target does not restart reaction delay.
- Exact final action rotation raycasts to the required entity/block after quantization.
- Queue/request replacement, module disable, world change, and reset clear all stale state.
- Prediction returns zero offset when disabled, confidence drops after a teleport, and projectile solver failure returns a safe unpredicted solution.

### Scenario metrics

Measure rather than hard-code a claim of humanity:

- acquisition time and time-to-valid-raycast;
- peak angular velocity/acceleration/jerk;
- velocity peak location and number of local peaks;
- path length/direct-distance ratio and maximum normal deviation;
- terminal error before and after quantization;
- correction and overshoot rates by angular-distance/target-width bucket;
- yaw/pitch delta correlation and sign bias;
- target-point dwell time and number of point changes per engagement;
- deadline misses, invalid raycasts, and placement/attack regressions;
- frame time and allocation count in the per-tick hot path.

Acceptance gates should be functional and comparative: zero invalid numeric outputs, zero unexplained deadline misses, no sustained post-completion drift, no target-point hopping on a stationary target, deterministic replay, and no measurable tick-time regression. Distribution targets should come from the client's opt-in manual trace corpus, not constants copied from cursor libraries.

### Stress and integration cases

- Repeated 1-GCD and sub-GCD requests.
- 10,000 alternating small rotations to expose residual drift.
- Continuous 180° target orbit and rapid target switching.
- Same-owner refresh versus higher-priority preemption.
- Low FPS/timer changes where multiple logical ticks or delayed ticks occur.
- Inventory open pauses and resumes.
- FreeCam, Derp, NoRotateSet, server position/look corrections, riding, and player respawn.
- Strict and non-strict strafe correction.
- Sensitivity changes during a movement (rebase quantizer state safely).
- Bounding box changes, partial occlusion, through-wall ranges, and disappearing entities.

## Performance requirements

- No allocation-heavy path list in the per-tick loop; retain a small state and evaluate the curve analytically.
- No coroutine, sleep, or wall-clock dependence in the engine.
- No raycast grid rescan solely for humanization on every tick. Cache the feasible region and invalidate it on material geometry/visibility changes; use a bounded fallback search.
- Target history must be bounded and cleared with world/entity lifecycle.
- Telemetry must be disabled by default and use a bounded buffer when enabled.

## Risks and mitigations

- **Too few samples at 20 Hz:** use the deterministic limiter for short moves and reserve curves for moves with at least three useful ticks.
- **Moving target invalidates a preplanned endpoint:** continuously retarget with velocity continuity and validate the quantized next step.
- **Humanization causes missed actions:** purpose/deadline/validity always overrides cosmetic effects; shrink variation or fall back deterministically.
- **Config explosion:** expose profiles plus four meaningful controls, keeping experimental coefficients developer-only.
- **Global-owner conflicts:** explicit request owner/priority and handoff state replace mutable flags on shared settings.
- **Random bugs cannot be reproduced:** one seeded RNG per session/engine, seed in telemetry, no `Math.random()` in the pipeline.
- **Overfitting to external implementations:** calibrate against client rotation recordings and gameplay outcomes, not pixel/USB constants.
- **Documentation/code drift:** keep profile values in one data structure and generate debug descriptions from it; tests assert preset bounds.

## Definition of done

The project is complete when all rotation-producing modules use the same request coordinator; prediction and humanization are separate services; legacy randomization options and duplicated algorithms are removed; generated rotations are deterministic under a seed, sensitivity-valid, deadline-aware, and raycast-safe; reset and target handoffs are smooth; pure tests and stress scenarios pass; and `PLAN.md`'s scenario metrics show no functional regression against the baseline.
